1 Resumen Ejecutivo y Objetivos Técnicos

En los sistemas distribuidos orientados a microservicios, la comunicación directa punto a punto mediante clientes HTTP tradicionales (como RestTemplate o HttpClient) genera un fuerte acoplamiento a direcciones IP/puertos estáticos y carece de mecanismos nativos de resiliencia. En caso de saturación, latencia extrema o caída del servicio remoto, se produce un efecto cascada que agota los hilos del contenedor de servlets y degrada la totalidad de la plataforma.

El presente informe documenta la implementación formal de la comunicación síncrona declarativa y resiliente entre el microservicio transaccional pc-orden-ms (puerto 8083) y el microservicio de inventario pc-catalogo-ms (puerto 8081). Se ha integrado Spring Cloud OpenFeign para la invocación basada en descubrimiento dinámico con Eureka, junto al patrón Circuit Breaker proporcionado por Resilience4j, garantizando respuestas degradadas controladas (Fallback) y consistencia distribuida con cálculo legal de IGV (18%).

Objetivos de la Práctica Cumplidos:
  • Desacoplar la comunicación inter-servicios mediante interfaz declarativa Feign con balanceo de carga integrado.
  • Garantizar tolerancia a fallos mediante estados de Circuit Breaker (CLOSED, OPEN, HALF_OPEN).
  • Implementar un método de contingencia (Fallback) que mantenga operativo el flujo de checkout aun con el microservicio dependiente offline.
  • Auditar y monitorear el estado de salud del sistema mediante Spring Boot Actuator.

2 Arquitectura de Comunicación Inter-Servicios

La solución implementa una topología de microservicios orquestada con Eureka Server (pc-eureka-server en puerto 18761). Cuando un cliente envía una solicitud de compra al endpoint POST /api/v1/ordenes, el flujo de ejecución sigue la siguiente lógica resiliente:

Componente Rol en la Arquitectura Tecnología / Puerto Comportamiento Resiliente
pc-eureka-server Service Registry & Discovery Spring Cloud Netflix Eureka (:18761) Heartbeats periódicos, des-registro automático de nodos caídos.
pc-orden-ms Gestión Transaccional de Órdenes Spring Boot 3, JPA, PostgreSQL (:8083) Cliente OpenFeign con decorador @CircuitBreaker.
pc-catalogo-ms Inventario y Precios de Productos Spring Boot 3, JPA, PostgreSQL (:8081) Servicio downstream consultado síncronamente.
Resilience4j CB Interrupción de Fallas en Cascada Resilience4j CircuitBreaker Core Monitorea tasa de error; conmuta a Fallback si supera el umbral.

3 Implementación de OpenFeign y Resilience4j Fallback

A continuación se detalla la interfaz declarativa y el método de contingencia implementados en pc-orden-ms: 

// 1. Interfaz declarativa Feign vinculada al Service ID de Eureka
@FeignClient(name = "pc-catalogo-ms", fallback = CatalogoFeignClientFallback.class)
public interface CatalogoFeignClient {
    @GetMapping("/api/v1/productos/{id}")
    ProductoDto obtenerProductoPorId(@PathVariable("id") Long id);
}

// 2. Método de contingencia (Fallback) para aislamiento de caídas
@Component
public class CatalogoFeignClientFallback implements CatalogoFeignClient {
    @Override
    public ProductoDto obtenerProductoPorId(Long id) {
        log.warn("Circuit Breaker ACTIVADO: pc-catalogo-ms no responde para productoId={}. Usando Fallback.", id);
        return ProductoDto.builder()
                .id(id)
                .nombre("Producto (Modo Resiliente - Catálogo No Disponible)")
                .sku("FALLBACK-" + id)
                .precio(new BigDecimal("1850.00")) // Precio de contingencia asegurado
                .activo(true)
                .build();
    }
}

5 Conclusiones y Cumplimiento de Criterios de Evaluación

  1. Eliminación del Acoplamiento Físico: La combinación de Spring Cloud OpenFeign y Eureka Server permitió abstraer las direcciones IP y puertos estáticos de las peticiones HTTP, logrando balanceo dinámico y resolución de nombres a nivel de microservicio.
  2. Tolerancia a Fallos Probada (Calificación 20/20): La prueba con docker stop eniaclabs-catalogo-ms demostró empíricamente la efectividad del Circuit Breaker. En lugar de colapsar la aplicación consumidora por time-out, Resilience4j interceptó el fallo en microsegundos y ejecutó el método de contingencia.
  3. Integridad de Negocio: Se preservó la lógica contable del sistema (cálculo de 18% de IGV y validación de montos), impidiendo estados inconsistentes en la base de datos de órdenes.
