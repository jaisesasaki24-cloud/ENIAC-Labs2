1 Resumen Ejecutivo y Objetivos Técnicos

En los sistemas distribuidos orientados a microservicios, la comunicación directa punto a punto mediante clientes HTTP tradicionales (como RestTemplate o HttpClient) genera un fuerte acoplamiento a direcciones IP/puertos estáticos y carece de mecanismos nativos de resiliencia. En caso de saturación, latencia extrema o caída del servicio remoto, se produce un efecto cascada que agota los hilos del contenedor de servlets y degrada la totalidad de la plataforma.

El presente informe documenta la implementación formal de la comunicación síncrona declarativa y resiliente entre el microservicio transaccional pc-orden-ms (puerto 8083) y el microservicio de inventario pc-catalogo-ms (puerto 8081). Se ha integrado Spring Cloud OpenFeign para la invocación basada en descubrimiento dinámico con Eureka, junto al patrón Circuit Breaker proporcionado por Resilience4j, garantizando respuestas degradadas controladas (Fallback) y consistencia distribuida con cálculo legal de IGV (18%).

Objetivos de la Práctica Cumplidos:
  • Desacoplar la comunicación inter-servicios mediante interfaz declarativa Feign con balanceo de carga integrado.
  • Garantizar tolerancia a fallos mediante estados de Circuit Breaker (CLOSED, OPEN, HALF_OPEN).
  • Implementar un método de contingencia (Fallback) que mantenga operativo el flujo de checkout aun con el microservicio dependiente offline.
  • Auditar y monitorear el estado de salud del sistema mediante Spring Boot Actuator.

2 Arquitectura de Comunicación Inter-Servicios

La solución implementa una topología de microservicios orquestada con Eureka Server (pc-eureka-server en puerto 18761). Cuando un cliente envía una solicitud de compra al endpoint POST /api/v1/ordenes, el flujo de ejecución sigue la siguiente lógica resiliente:

Componente Rol en la Arquitectura Tecnología / Puerto Comportamiento Resiliente

pc-orden-ms Gestión Transaccional de Órdenes Spring Boot 3, JPA, PostgreSQL (:8083) Cliente OpenFeign con decorador @CircuitBreaker.
pc-catalogo-ms Inventario y Precios de Productos Spring Boot 3, JPA, PostgreSQL (:8081) Servicio downstream consultado síncronamente.

3 Implementación de OpenFeign y Resilience4j Fallback

A continuación se detalla la interfaz declarativa y el método de contingencia implementados en pc-orden-ms: 

// 1. Interfaz declarativa Feign vinculada al Service ID de Eureka
@FeignClient(name = "pc-catalogo-ms", fallback = CatalogoFeignClientFallback.class)
public interface CatalogoFeignClient {
    @GetMapping("/api/v1/productos/{id}")
    ProductoDto obtenerProductoPorId(@PathVariable("id") Long id);
}

// 2. Método de contingencia (Fallback) para aislamiento de caídas
@Component
public class CatalogoFeignClientFallback implements CatalogoFeignClient {
    @Override
    public ProductoDto obtenerProductoPorId(Long id) {
        log.warn("Circuit Breaker ACTIVADO: pc-catalogo-ms no responde para productoId={}. Usando Fallback.", id);
        return ProductoDto.builder()
                .id(id)
                .nombre("Producto (Modo Resiliente - Catálogo No Disponible)")
                .sku("FALLBACK-" + id)
                .precio(new BigDecimal("1850.00")) // Precio de contingencia asegurado
                .activo(true)
                .build();
    }
}

6 Error o Hallazgo Técnico Resuelto

Hallazgo Crítico: Auto-invocación de Métodos y Omisión del Proxy de Spring AOP

Durante la implementación inicial de @CircuitBreaker en OrdenServiceImpl, los métodos consultarPrecio() y fallbackConsultarPrecio() se definieron dentro de la misma clase del servicio. Aunque el código compilaba sin advertencias, al detener el microservicio de catálogo (pc-catalogo-ms), la llamada fallaba arrojando una excepción FeignException: Connection Refused (HTTP 500) sin ejecutar el fallback.

Causa Raíz: Resilience4j opera mediante un proxy dinámico de Spring AOP. Las invocaciones internas entre métodos de una misma instancia (this.consultarPrecio(...)) eluden el interceptor AOP de Spring.

Solución Aplicada: Se extrajo la invocación de catálogo a un componente Spring independiente: ProductoConsultaService. Al inyectar dicho servicio en OrdenServiceImpl, la llamada cruza el límite del bean y activa el proxy AOP de Resilience4j correctamente, garantizando la interceptación del error y la ejecución inmediata del fallback.

7 Reflexión Técnica Breve (Timeout vs. Circuit Breaker)

Proteger una llamada entre microservicios con un Circuit Breaker es conceptual y operativamente distinto de simplemente incrementar el timeout. Aumentar el tiempo de espera no soluciona una dependencia caída; por el contrario, retiene los hilos del servidor Tomcat en espera bloqueante, provocando agotamiento del pool de conexiones (Thread Starvation) y contagiando el colapso al resto del ecosistema (Cascading Failure). En cambio, el Circuit Breaker evalúa la tasa histórica de fallos mediante una ventana deslizante: al superar el umbral configurado, conmuta al estado OPEN e interrumpe de inmediato las llamadas físicas (Fail-Fast a 0 ms), ejecutando el fallback de contingencia y otorgando una ventana de recuperación al microservicio dependiente.

8 Respuestas a las Preguntas de Defensa (Sección 4.5)

Pregunta de Evaluación Sustentación Técnica (Arquitectura ENIAC Labs)
1. ¿Por qué producto_id en ordenes_compra_detalle no lleva FOREIGN KEY, a diferencia de orden_compra_id? orden_compra_id apunta a una entidad dentro del mismo agregado en la base de datos eniaclabs_orden_db, por lo que la integridad referencial se garantiza a nivel de motor SQL. En cambio, producto_id pertenece al microservicio pc-catalogo-ms con su propio esquema independiente (Database-per-Service). Forzar una clave foránea violaría el desacoplamiento de datos y la autonomía de despliegue.
2. ¿Qué problema resuelve Feign que no resolvía llamar a pc-catalogo-ms con una dirección fija? Una dirección fija (ej. http://localhost:8081) impide el balanceo de carga dinámico y falla cuando los contenedores escalan o cambian de IP en Docker/K8s. OpenFeign se integra con Eureka (Client-Side Discovery), resolviendo el nombre lógico pc-catalogo-ms y distribuyendo las llamadas entre instancias sanas.
3. ¿Qué diferencia hay entre un timeout y un Circuit Breaker? Un timeout solo decide cuánto esperar en una petición individual antes de fallar. Un Circuit Breaker mantiene memoria estadística de fallos recientes: al sobrepasar el umbral (ej. 50%), pasa a OPEN y rechaza llamadas de inmediato sin esperar timeouts de red.
4. ¿Qué pasa con una orden si pc-catalogo-ms está caído, y por qué es mejor que un error 500? Se activa el método fallback y la orden se retiene en un estado controlado (CARRITO o con precio de contingencia asegurado) sin total definitivo. Es superior a un error 500 porque no rompe la experiencia del usuario y evita caídas en cascada de los recursos del servidor.
5. ¿Cómo demuestras que el circuito pasó de CLOSED a OPEN? Se demuestra verificando: (a) latencia de respuesta reducida a milisegundos (0 ms sin espera de timeout), (b) logs de auditoría registrando Circuit Breaker activado (Fallback), y (c) consulta de métricas en Actuator /actuator/metrics/resilience4j.circuitbreaker.state?tag=state:open.
