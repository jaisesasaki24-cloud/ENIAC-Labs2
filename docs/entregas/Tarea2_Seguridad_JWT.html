1. Arquitectura y Enlaces Directos al Código

El sistema elimina por completo la suplantación de identidad en compras gamers mediante un flujo stateless sustentado en OAuth2 / OpenID Connect:

Componente Ubicación en GitHub Rol en la Solución
Controlador de Autenticación AuthController.java Endpoints públicos de /login, /register y validación.
Generador de JWT (RS256) JwtTokenProvider.java Firma asimétrica RSA con claims estándar (sub, idCliente, realm_access.roles).
Filtro Perimetral Gateway JwtAuthenticationFilter.java Valida firma contra JWKS y propaga contexto de seguridad en cabeceras.
Configuración RBAC Gateway SecurityConfig.java Reglas de acceso por roles (ADMIN para catálogo, CLIENTE para órdenes).
Extracción de Claims en Orden OrdenServiceImpl.java Cero confianza en el request: lee el cliente de @AuthenticationPrincipal Jwt.

3. Preguntas de Defensa Técnica y Sustentación

  • ¿Por qué se utilizó RS256 (asimétrico) en vez de HS256 (simétrico)?
    Respuesta: Con HS256, si un microservicio interno es vulnerado, el atacante obtiene la clave secreta y puede firmar tokens falsos. Con RS256, solo pc-auth-ms guarda la clave privada. Los demás servicios (Gateway, Órdenes) solo consumen la clave pública (JWKS) para verificar la firma, aislando el riesgo.
  • ¿Qué pasaría si un atacante intenta llamar directamente a `pc-orden-ms` (:8083) sin pasar por el Gateway?
    Respuesta: Siguiendo el principio de Defensa en Profundidad (Zero Trust), pc-orden-ms es también un Resource Server configurado con Spring Security. Rechazará la llamada con 401 Unauthorized a menos que se presente un JWT válido con firma verificada.
  • ¿Cómo se relaciona esta arquitectura con Keycloak en producción?
    Respuesta: Al haberse diseñado bajo el estándar OAuth2 / OIDC con formato JWKS y claims realm_access.roles, reemplazar pc-auth-ms por un clúster Keycloak en producción solo requiere cambiar la URL de issuer-uri en el Config Server, sin alterar ninguna línea de código Java.
