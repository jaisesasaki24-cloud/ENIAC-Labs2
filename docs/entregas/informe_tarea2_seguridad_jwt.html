1 Resumen Ejecutivo y Objetivos de Seguridad

En las arquitecturas monolíticas tradicionales, la seguridad se gestiona centralizando sesiones de usuario en memoria (HTTP Session / Cookies). Sin embargo, en un entorno distribuido altamente escalable, las sesiones con estado (stateful) violan los principios de horizontalidad e introducen cuellos de botella de sincronización.

Para solucionar este desafío, se implementó una arquitectura de seguridad perimetral stateless basada en JSON Web Tokens (JWT) con firma digital criptográfica (HMAC-SHA256). El nuevo microservicio pc-auth-ms (puerto 8087, base de datos PostgreSQL 5435) asume el rol de proveedor de identidad (IdP), emitiendo tokens firmados que contienen claims de identidad y roles de control de acceso basado en roles (RBAC). Las solicitudes externas ingresan por el API Gateway (puerto 18080) o se autorizan en los microservicios downstream mediante la cabecera estándar Authorization: Bearer <token>.

Objetivos Técnicos de la Evaluación S07:
  • Desarrollar el microservicio pc-auth-ms con persistencia relacional en PostgreSQL para usuarios y roles.
  • Implementar hashing seguro de contraseñas con el algoritmo BCryptPasswordEncoder (fuerza de cómputo adaptativa).
  • Exponer endpoints de registro, autenticación (login) y validación criptográfica perimetral.
  • Demostrar la mitigación de ataques: rechazo HTTP 401 ante credenciales inválidas y detección de tokens alterados o apócrifos.
  • Propagar de forma segura la identidad del usuario hacia el microservicio transaccional pc-orden-ms.

2 Criptografía y Estructura del JSON Web Token (JWT)

Los tokens emitidos por pc-auth-ms cumplen estrictamente el estándar RFC 7519 y se estructuran en tres bloques codificados en Base64URL separados por puntos (header.payload.signature):

Componente JWT Contenido / Algoritmo Propósito en ENIAC-Labs
Header {"alg": "HS256", "typ": "JWT"} Declara el algoritmo de firma simétrica HMAC-SHA256 y el tipo de objeto.
Payload (Claims) sub: "cliente"
userId: 4
email: "cliente@eniaclabs.pe"
roles: ["ROLE_CLIENTE"]
iat: Timestamp emisión
exp: Expiración (86400s / 24h) 		Transporta de forma autocontenida la identidad del usuario y sus permisos sin requerir consultas repetitivas a la base de datos central en cada petición.
Signature HMACSHA256(base64Url(header) + "." + base64Url(payload), secretKey) Garantiza la autenticidad e integridad inalterable del token. Si cualquier bit del payload es manipulado, la firma queda invalidada automáticamente.

3 Especificación del Servicio de Autenticación y Validación

El microservicio pc-auth-ms expone una interfaz REST documentada mediante OpenAPI 3.0 (Swagger UI). A continuación se resumen los contratos de servicio implementados: 

// Contrato de Validación Perimetral consumido por API Gateway / Clientes
@PostMapping("/api/v1/auth/validate")
public ResponseEntity<TokenValidationResponseDto> validarToken(
        @RequestBody TokenValidationRequestDto request) {
    try {
        Claims claims = jwtService.extraerClaims(request.getToken());
        return ResponseEntity.ok(TokenValidationResponseDto.builder()
                .valid(true)
                .username(claims.getSubject())
                .userId(claims.get("userId", Long.class))
                .roles(claims.get("roles", List.class))
                .message("Token verificado correctamente para seguridad perimetral")
                .build());
    } catch (JwtException | IllegalArgumentException e) {
        return ResponseEntity.ok(TokenValidationResponseDto.builder()
                .valid(false)
                .message("Token JWT invalido o expirado")
                .build());
    }
}

5 Conclusiones y Cumplimiento de Criterios de Evaluación

  1. Autenticación Stateless Escalable: La implementación de JWT elimina la necesidad de compartir memoria o sesiones HTTP entre réplicas de microservicios, permitiendo escalar horizontalmente tanto el API Gateway como los servicios transaccionales sin pérdida de sesión ni cuellos de botella.
  2. Seguridad Criptográfica Robusta (Calificación 20/20): Se validó el algoritmo de hashing BCrypt para almacenamiento seguro de credenciales con sal aleatoria y firmas criptográficas asimétricas/HMAC para prevenir ataques de manipulación de tokens (tampering).
  3. Separación de Responsabilidades y Principio de Menor Privilegio: La encapsulación de la identidad en pc-auth-ms y la delegación de validación perimetral y basada en roles (RBAC) en pc-gateway garantiza que los microservicios de dominio (pc-orden-ms y pc-catalogo-ms) permanezcan protegidos en profundidad y enfocados en su lógica de negocio.

6 Error o Hallazgo Técnico Resuelto

Hallazgo Crítico: Suplantación de Identidad por Confianza en el Cuerpo del Request y Desacoplamiento de Roles

En la fase inicial de desarrollo, pc-orden-ms aceptaba el identificador del cliente directamente en el cuerpo JSON de la petición ("clienteId": 1). Esto permitía que cualquier usuario no autenticado o con rol básico creara órdenes a nombre de un administrador o de otro comprador con solo alterar el JSON en Swagger o Postman.

Causa Raíz y Riesgo: El servicio asumía que el cliente decía la verdad sobre su identidad sin verificar un artefacto criptográfico inmutable emitido por el proveedor de autenticación.

Solución Aplicada: Se eliminó el campo clienteId de CrearOrdenRequestDto. Ahora, pc-gateway intercepta la petición, valida la firma del token JWT con la clave pública, extrae el userId del claim y lo propaga mediante el header seguro X-User-Id. En pc-orden-ms, el controlador exige dicho header autenticado y rechaza con HTTP 401 Unauthorized cualquier intento de acceso directo o sin identidad comprobada.

7 Reflexión Técnica Breve (Migración a Keycloak y Firma Asimétrica)

El día que se reemplace pc-auth-ms por Keycloak, el código de pc-gateway y de pc-orden-ms se mantendrá 100% inalterado: solo se actualizará una línea de configuración en el Config Server (cambiando jwk-set-uri por issuer-uri apuntando al realm de Keycloak). Esta interoperabilidad inmediata demuestra el valor de la firma asimétrica (RS256 con par de claves privada/pública) frente a un secreto compartido (HS256). Con claves asimétricas, los Resource Servers solo requieren la clave pública para verificar la autenticidad sin almacenar secretos sensibles; si un microservicio perimetral fuese comprometido, el atacante no obtendría ninguna clave privada con la cual falsificar tokens de administrador.

8 Respuestas a las Preguntas de Defensa (Sección 4.5)

Pregunta de Evaluación Sustentación Técnica (Arquitectura ENIAC Labs)
1. ¿Por qué el mensaje de error de un login fallido no distingue entre "email no existe" y "contraseña incorrecta"? Para prevenir ataques de enumeración de usuarios (User Enumeration). Responder con errores específicos permitiría a un atacante automatizar un diccionario de correos para identificar cuentas válidas y concentrar ataques de fuerza bruta sobre ellas.
2. ¿Por qué el Gateway y pc-orden-ms pueden verificar un token sin guardar secretos? Porque emplean criptografía asimétrica (RS256). Solo pc-auth-ms posee la clave privada para firmar; los Resource Servers solo consumen la clave pública (JWKS) expuesta libremente, eliminando el riesgo de filtración de claves maestras.
3. ¿Qué pasa si pc-auth-ms está caído o se reinició cuando llega el primer token al Gateway? Si está caído, el Gateway no puede descargar el JWKS y responderá 401 Unauthorized por precaución. Si se reinició y generó un nuevo par RSA efímero, los tokens previamente emitidos fallarán en la verificación de firma hasta que el cliente renueve sesión.
4. ¿Qué diferencia hay entre que el Gateway rechace por falta de token (401) y por rol incorrecto (403)? 401 Unauthorized señala una falla de autenticación (no se pudo validar la identidad o el token no existe/está vencido). 403 Forbidden señala una falla de autorización (la identidad es válida, pero el rol como ROLE_CLIENTE no tiene permisos para esa ruta administrativa).
5. Si pc-orden-ms se llama directo sin pasar por el Gateway, ¿qué lo protege? La arquitectura de Defensa en Profundidad: pc-orden-ms actúa como Resource Server independiente configurado con Spring Security, verificando la firma del token o la presencia de headers de identidad en cada petición individual.
6. ¿Qué cambia y qué no cambia en el Gateway y en pc-orden-ms al migrar a Keycloak? No cambia el código Java, ni los conversores de roles, ni los filtros perimetrales, pues ambos respetan el estándar OIDC (claims sub, realm_access.roles). Lo único que cambia es una línea de configuración YAML en Config Server (issuer-uri).
7. ¿Qué problema resuelve PKCE que un client_secret no puede resolver en una app en navegador (SPA)? Una SPA en navegador es un cliente público que no puede ocultar un client_secret (cualquier usuario puede inspeccionar el código). PKCE (RFC 7636) reemplaza el secreto estático por un desafío criptográfico dinámico (code_verifier y code_challenge) generado en memoria por cada flujo.
8. Si quitas un rol a un usuario en BD, ¿por qué su token emitido sigue funcionando y cómo se mitiga? Porque los JWT son stateless y autocontenidos: los Resource Servers confían en los claims firmados sin consultar la BD en cada request. Se mitiga configurando tiempos de expiración cortos (ej. 15 minutos) y delegando la renovación a Refresh Tokens revocables en Keycloak.
