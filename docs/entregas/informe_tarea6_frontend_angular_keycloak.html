1 Migración a Keycloak IAM y Configuración del Realm
✓ Verificación del Sistema: 2026-10-18 | Usuario: USUARIO | Rúbrica Criterio 1: 25% (Nivel A: 20 pts)

El ecosistema de ENIAC Labs completó la migración desde un servidor de autenticación temporal hacia Keycloak 26 como único proveedor de identidad (IdP) federado:

  • Realm: eniaclabs configurado con estándar OpenID Connect.
  • Cliente Público SPA: eniaclabs-frontend con Standard Flow Enabled (Authorization Code), Direct Access Grants Disabled (bloqueando el intercambio inseguro de usuario/contraseña directo), y Proof Key for Code Exchange (PKCE) obligatorio en modo S256.
  • Gestión del Identificador de Cliente: Se estableció que el dato de negocio idCliente es exactamente el claim estándar sub del JWT emitido por Keycloak. Esto desacopla el modelo de datos de identificadores numéricos locales secuenciales y garantiza unicidad en todo el clúster distribuido.
  • Roles en Token: Los roles CLIENTE y ADMIN se emiten bajo el nodo realm_access.roles y son leídos tanto por el Gateway como por la SPA.

2 Cliente Angular 22 con Authorization Code + PKCE y CORS Centralizado
✓ Verificación del Sistema: 2026-10-18 | Usuario: USUARIO | Rúbrica Criterio 2: 25% (Nivel A: 20 pts)

Siguiendo los lineamientos de seguridad de RFC 7636 y RFC 9700, la SPA clients/eniaclabs-frontend implementa el flujo de autenticación seguro:

Mecanismo / Elemento Implementación en ENIAC Labs Propósito de Seguridad
Generación de PKCE generarCodeVerifier() (32 bytes aleatorios) y generarCodeChallenge() (SHA-256 + Base64Url). Evita la interceptación del código de autorización por aplicaciones maliciosas en el mismo host.
Parámetro state Anti-CSRF 16 bytes aleatorios guardados en sessionStorage y comparados estrictamente en /auth/callback. Previene ataques de fijación de sesión y falsificación de peticiones en el flujo de retorno.
Almacenamiento de Tokens En Memoria (Signal Angular reactivo en AuthService). Protección absoluta contra robo de sesión por inyección XSS (nunca se almacena en localStorage).
CORS en el Gateway CorsConfig.java y .cors(cors -> {}) en infra/pc-gateway. Punto único de configuración para todos los microservicios sin duplicación de cabeceras en el navegador.

export function generarCodeVerifier(): string { return base64UrlEncode(crypto.getRandomValues(new Uint8Array(32))); } export async function generarCodeChallenge(verifier: string): Promise<string> { const hash = await crypto.subtle.digest('SHA-256', new TextEncoder().encode(verifier)); return base64UrlEncode(new Uint8Array(hash)); }
3 Consistencia Eventual en la Interfaz (Estrategia de Polling)
✓ Verificación del Sistema: 2026-10-18 | Usuario: USUARIO | Rúbrica Criterio 3: 25% (Nivel A: 20 pts)

En una arquitectura distribuida donde la comunicación entre órdenes y pagos es asíncrona mediante Apache Kafka (S08 y S09), una respuesta HTTP 201 Created en POST /api/v1/ordenes significa que la orden fue registrada con éxito en estado PENDIENTE_PAGO, no que el pago haya sido aprobado.

Justificación de la Estrategia Elegida: Sondeo Periódico Inteligente (Polling)
Se descartó la Recarga Manual por trasladar la incertidumbre al usuario, y se prefirió Polling Periódico Acotado frente a WebSockets para mantener una arquitectura ligera sin brokers de sockets adicionales en el Gateway. El componente MisPedidos ejecuta un intervalo cada 4000ms optimizado: (1) Solo re-consulta órdenes en estado PENDIENTE_PAGO; (2) Cuando la orden pasa a PAGADA o CANCELADA, se excluye del sondeo y se consulta su detalle en GET /api/v1/pagos/por-orden/{ordenId}; (3) Al destruir la vista (ngOnDestroy), se cancela el intervalo (clearInterval) eliminando tráfico ocioso.

private refrescarPendientes(): void { const pendientes = this.pedidos().filter((p) => p.orden.estado === 'PENDIENTE_PAGO'); for (const pendiente of pendientes) { this.ordenService.obtener(pendiente.orden.id).subscribe((actualizada) => { this.pedidos.update((lista) => lista.map((p) => (p.orden.id === actualizada.id ? { ...p, orden: actualizada } : p)), ); if (actualizada.estado !== 'PENDIENTE_PAGO') { this.cargarPago(actualizada.id); // Consulta detalle en pc-pago-ms } }); } }

5 Error Técnico Diagnosticado y Hallazgo de Arquitectura
Error Diagnosticado: Preflight CORS (401 Unauthorized en peticiones OPTIONS)
Al integrar el cliente Angular corriendo en http://localhost:4200 con el Gateway en http://localhost:18080, las peticiones con métodos no simples (e.g. POST /api/v1/ordenes o PUT /api/v1/categorias/1) fallaban silenciosamente en el navegador con un error de CORS.

Causa Raíz: El navegador envía primero una petición de verificación (Preflight OPTIONS). Esta petición previa no transporta cabeceras Authorization. Al estar configurado .cors(AbstractHttpConfigurer::disable) en SecurityConfig.java de pc-gateway, Spring Security interceptaba el OPTIONS y, al no hallar token JWT, respondía 401 Unauthorized antes de que se pudieran adjuntar las cabeceras Access-Control-Allow-Origin.

Solución Implementada: Se creó el bean CorsConfig.java con CorsConfigurationSource admitiendo el origen http://localhost:4200 y se habilitó .cors(cors -> {}) en la cadena de seguridad de Spring Security para dejar pasar automáticamente las peticiones OPTIONS sin exigir credenciales.
Hallazgo 2: Aislamiento de llamadas a Keycloak en AuthService (fetch vs HttpClient)
El interceptor global authInterceptor se registra sobre HttpClient para inyectar automáticamente la cabecera Authorization: Bearer <token> en las llamadas al Gateway. Si la llamada de canje de código en completarLogin() se realizara con HttpClient, se produciría una contradicción de arquitectura: Keycloak exige application/x-www-form-urlencoded sin token previo. Se empleó fetch() nativo para aislar el flujo de obtención de credenciales del pipeline HTTP del negocio.
6 Reflexión Técnica: Incidente Starbucks y Consistencia en la UI

"El incidente de las tarjetas de regalo de Starbucks (2015) demostró que una condición de carrera no es únicamente una vulnerabilidad de concurrencia en la base de datos, sino un fallo estructural de consistencia que destruye la seguridad del negocio. Si dos operaciones concurrentes leen el mismo estado antes de que se serialice el descuento, el saldo se duplica de forma ilegítima. En ENIAC Labs, esta lección se aplicó directamente al diseño de la interfaz: el frontend nunca asume que una respuesta HTTP 201 equivale a 'pedido pagado'. La interfaz refleja honestamente el estado transitorio PENDIENTE_PAGO y bloquea envíos duplicados con [disabled]='enviando()', mientras que el backend protege la transacción con consumidores idempotentes en Kafka y restricciones de integridad en PostgreSQL."

7 Preguntas de Defensa Técnica (Sección 4.5)
1. ¿Por qué se decidió que idCliente podía ser literalmente sub, en vez de usar un protocol mapper ad-hoc?
Porque el claim sub (Subject) es el identificador único universal (UUID) que OpenID Connect garantiza para cada usuario autenticado en Keycloak. Crear un mapper personalizado para mapear un id numérico manual duplica la complejidad administrativa y no escala al registrar nuevos clientes gamer. Al migrar la columna id_cliente en PostgreSQL a VARCHAR(36), sub se convirtió en la clave foránea natural entre identidad y órdenes.
2. ¿Qué problema concreto previene verificar state al volver de Keycloak, y qué pasaría si tu cliente lo ignorara?
Previene ataques de Cross-Site Request Forgery (CSRF) y fijación de sesión. Si el cliente ignorara el state, un atacante podría engañar a la víctima para que complete un flujo de autorización con un código perteneciente a la cuenta del atacante, vinculando transacciones o tarjetas a una sesión ajena sin que la víctima lo advierta.
3. ¿Por qué una respuesta 201 de POST /api/v1/ordenes no es evidencia de que el pago se resolvió?
Porque en una arquitectura basada en eventos (Event-Driven con Kafka), el microservicio de órdenes solo realiza la reserva de inventario y publica el evento orden.creada de forma asíncrona. El cobro real en la pasarela lo ejecuta pc-pago-ms en otro hilo y proceso independiente; la respuesta 201 solo confirma que la orden existe en estado PENDIENTE_PAGO.
4. De las tres estrategias de la Tabla 3, ¿cuál elegiste para tu propio proyecto, y qué te hizo descartar las otras dos?
Elegimos Polling Inteligente cada 4 segundos. Descartamos la Recarga Manual porque ofrece una pésima experiencia de usuario al comprar componentes de PC gamer. Descartamos WebSockets para no añadir la sobrecarga de mantener conexiones persistentes ni proxies adicionales en el API Gateway para esta etapa.
5. ¿Por qué el Gateway es el lugar correcto para configurar CORS, y no cada microservicio por separado?
Porque el Gateway es el punto único de entrada perimetral de la arquitectura. Configurarlo en el Gateway protege a todos los microservicios aguas abajo sin requerir cambios de código ni configuración en cada servicio individual. Además, evita el error del navegador por cabeceras duplicadas (multiple Access-Control-Allow-Origin values).
6. Si GET /api/v1/ordenes no filtra por idCliente en el backend, ¿qué protege realmente el filtrado en el frontend y qué no?
El filtrado en el frontend (filter(o => o.idCliente === auth.idCliente())) es una optimización de Experiencia de Usuario (UX) para mostrar solo los pedidos pertinentes al usuario. No es una barrera de seguridad: cualquier usuario técnico podría invocar el endpoint vía Swagger o curl y recibir el listado completo de órdenes. La verdadera seguridad debe residir en el backend mediante @PreAuthorize o filtros de persistencia.
