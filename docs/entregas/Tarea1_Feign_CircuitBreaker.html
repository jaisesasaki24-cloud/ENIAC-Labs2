1. Arquitectura y Componentes Implementados

El microservicio transaccional pc-orden-ms (puerto :8083) no almacena duplicados del catálogo gamer, cumpliendo con el principio Database-per-Service. Al registrar una orden de compra, consulta en tiempo real a pc-catalogo-ms (puerto :8081) a través de su nombre lógico registrado en pc-eureka.

Elemento Técnico Ubicación en GitHub Función y Propósito
Cliente OpenFeign CatalogoFeignClient.java Llamada síncrona declarativa hacia lb://pc-catalogo-ms/api/v1/productos/{id}.
Servicio de Resiliencia ProductoConsultaService.java Anotado con @CircuitBreaker(name = "catalogoCB", fallbackMethod = "...").
Lógica Transaccional OrdenServiceImpl.java Cálculo del IGV (18%), validación de stock y snapshot de precios inmutables.
Configuración Resilience4j pc-orden-ms-dev.yml Sliding window de 5 llamadas, threshold de fallo del 50%, waitDurationInOpenState de 10s.

Al detener o saturar pc-catalogo-ms, el método fallback captura la excepción CallNotPermittedException o FeignException y devuelve una respuesta controlada y segura:

3. Preguntas de Defensa Técnica y Sustentación

  • ¿Por qué se eligió OpenFeign sobre un RestTemplate simple?
    Respuesta: OpenFeign es declarativo, reduce drásticamente el código boilerplate de serialización HTTP y se integra de forma nativa con Spring Cloud LoadBalancer y Eureka para resolver nombres lógicos (lb://pc-catalogo-ms) sin IPs fijas.
  • ¿Por qué no copiar la tabla de productos dentro de `pc-orden-ms`?
    Respuesta: Viola el principio de microservicios Database-per-Service y generaría inconsistencia de datos inmediata al actualizar precios o stock. La orden solo retiene un snapshot pactado en la transacción.
  • ¿Qué ventaja aporta el estado OPEN ante una caída masiva?
    Respuesta: Aplica el patrón Fail-Fast. En lugar de mantener hilos bloqueados durante segundos esperando timeouts de red (lo que provocaría Cascading Failure y colapso de memoria), rechaza la petición en 0 milisegundos ejecutando el fallback.
